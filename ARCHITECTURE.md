## Слоистая архитектура

```
handler → service → repository → pgx → PostgreSQL
                ↘ accrual.Client → accrual-система
```

1. **handler** — HTTP-хендлеры на chi. Не импортирует `repository` — сервис возвращает `OrderDTO` и `WithdrawalDTO`. Проверяет только sentinel-ошибки из `service`.
2. **service** — бизнес-логика, bcrypt, каналы, воркеры. Транслирует ошибки `repository` в собственные sentinel-ошибки. Обращается к accrual-системе через интерфейс `AccrualClient`, что позволит подменять моком в тестах.
3. **repository** — хранилище на pgx. Использует приватный интерфейс `dbtx` (реализуется `*pgxpool.Pool`) — для unit-тестов без живой БД. Внутри транзакций код работает с `pgx.Tx` напрямую.
4. **accrual.Client** — HTTP-клиент с таймаутом 5 секунд, парсинг `Retry-After` при 429, ретраи для 5xx-ошибок (до 3 попыток с задержкой 1 секунда).

## Логирование

Логирование построено на `go.uber.org/zap` без глобальных переменных. `logger.Initialize` создаёт корневой логгер и возвращает его в `main`. В `main` от корневого логгера создаются дочерние через `logger.With(zap.String("component", "..."))` — каждый компонент получает свой логгер с полем `component`:

| Компонент | Значение `component` | Кому передаётся |
|---|---|---|
| main | `"main"` | `main.go` — запуск, shutdown |
| handler | `"handler"` | `Router` и `WithLogging` middleware |
| service | `"service"` | `GopherMart` |
| accrual | `"accrual"` | `accrual.Client` |

Если логгер не передан — компонент использует `zap.NewNop()`. Все имена полей в логах — на английском (`order`, `worker`, `attempt`, `retry_after` и т.д.).

## Схема базы данных

Три таблицы, одна миграция (`0001_init.up.sql`).

### Тип `order_status`

```sql
CREATE TYPE order_status AS ENUM ('NEW', 'PROCESSING', 'INVALID', 'PROCESSED');
```

PostgreSQL проверяет корректность значения на уровне БД — некорректный статус будет отклонён. При параметризованной вставке/обновлении используется явный cast `$1::order_status`, так как pgx v5 отправляет строковые параметры с OID `text`, а PostgreSQL не имеет неявного приведения `text → enum`.

### Таблица `users`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | идентификатор |
| `login` | `VARCHAR(255) NOT NULL` | логин (уникален, `UNIQUE` constraint) |
| `password_hash` | `VARCHAR(255) NOT NULL` | bcrypt-хеш пароля |
| `balance` | `NUMERIC(12,2) NOT NULL DEFAULT 0` | текущий баланс баллов |
| `withdrawn` | `NUMERIC(12,2) NOT NULL DEFAULT 0` | суммарное списание |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | время регистрации |

Баланс и списания хранятся прямо в таблице пользователей — отдельной таблицы транзакций нет. Это упрощает чтение (`GET /balance` — один `SELECT`), но усложнит возможный аудит (нет истории изменений баланса).

### Таблица `orders`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | идентификатор |
| `number` | `VARCHAR(32) NOT NULL` | номер заказа (уникален глобально, `UNIQUE` constraint) |
| `user_id` | `BIGINT NOT NULL REFERENCES users(id)` | владелец |
| `status` | `order_status NOT NULL DEFAULT 'NEW'` | внутренний статус (ENUM) |
| `accrual` | `NUMERIC(12,2) NOT NULL DEFAULT 0` | начисленные баллы |
| `uploaded_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | время загрузки |

Индексы: `idx_orders_user_id` (для `ListUserOrders`), `idx_orders_status` (для `ListPendingOrderNumbers`).

Колонка `number` уникальна глобально — один и тот же номер заказа не может быть загружен двумя разными пользователями. На уровне БД это unique constraint, на уровне хендлера — ответ с кодом 409 (заказ загружен другим пользователем).

### Таблица `withdrawals`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | идентификатор |
| `user_id` | `BIGINT NOT NULL REFERENCES users(id)` | кто списал |
| `order_number` | `VARCHAR(32) NOT NULL` | номер заказа |
| `sum` | `NUMERIC(12,2) NOT NULL` | сумма списания |
| `processed_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | время списания |

Индекс: `idx_withdrawals_user_id`. Внешний ключ `order_number` → `orders.number` не наложен, хотя заказ создаётся в той же транзакции.

### Транзакция списания `WithdrawPoints`

Четыре шага в одной транзакции:

1. `pg_advisory_xact_lock($userID)` — сериализация операций по пользователю. Блокировка транзакционная (снимается при commit/rollback), не требует явного освобождения.
2. `UPDATE users SET balance = balance - sum, withdrawn = withdrawn + sum WHERE id = $userID AND balance >= sum RETURNING balance` — атомарная проверка и списание. Если получим `ErrNoRows`, то сервису вернём `ErrInsufficientFunds` (ответ с кодом 402, недостаточно средств).
3. `INSERT INTO orders (number, user_id, status) VALUES ($1, $2, 'PROCESSED')` — создание заказа. Статус `PROCESSED` используется, чтобы не запрашивать начислений по заказу, в счёт которого выполняется списание баллов. На unique constraint violation возвращаем `ErrOrderAlreadyExists` (транзакция откатывается, ответ с кодом 422).
4. `INSERT INTO withdrawals (user_id, order_number, sum) VALUES ($1, $2, $3)` — фиксация факта списания.

**Почему используется `pg_advisory_xact_lock`, а не `SELECT FOR UPDATE`.** Advisory lock не блокирует строку, а только «замок» по ID пользователя. Нет необходимости держать строку заблокированной до конца транзакции, нет риска deadlock при неаккуратном порядке блокировок. Субъективно при этом подходе код выглядит чище.

**Замечание о коде 422.** Спецификация для `POST /api/user/balance/withdraw` перечисляет коды 200, 401, 402, 422, 500. Код 422 описан как «неверный номер заказа», но 409 (Conflict) отсутствует в списке допустимых. Поэтому 422 используется расширительно — и для неверного номера заказа (не проходит Лун-проверку), и для случая, когда заказ уже использован другим списанием.

## HTTP-хендлеры

### `POST /api/user/register` — регистрация пользователя

1. Чтение JSON-тела запроса с полями `login` и `password` (макс. 4096 байт).
2. Проверка, что логин и пароль непусты. Если пусты — 400.
3. Вызов `service.RegisterUser`: пароль хешируется через bcrypt (cost 12), в БД сохраняется только хеш.
4. Если логин уже занят — 409.
5. При успехе — генерация JWT (HS256, TTL 24 часа), установка cookie `gophermart_auth` с параметрами `HttpOnly: true`, `SameSite: Strict`, `Path: /`.
6. Ответ 200.

### `POST /api/user/login` — аутентификация пользователя

1. Чтение JSON-тела с полями `login` и `password` (макс. 4096 байт).
2. Проверка, что логин и пароль непусты. Если пусты — 400.
3. Вызов `service.AuthenticateUser`: поиск пользователя по логину, сравнение пароля через `bcrypt.CompareHashAndPassword`.
4. Если пользователь не найден или пароль не совпадает — 401.
5. При успехе — генерация JWT и установка cookie, аналогично регистрации.
6. Ответ 200.

**Особенности.** Пароли в БД не хранятся — только bcrypt-хеши. Сервисный слой транслирует ошибки хранилища в собственные sentinel-ошибки, поэтому хендлер работает только с типами из пакета `service` и не импортирует `repository`.

### `POST /api/user/orders` — загрузка номера заказа

1. Извлечение ID пользователя из контекста (через middleware `RequireAuth`).
2. Чтение тела запроса как `text/plain` (макс. 64 байта). `strings.TrimSpace` убирает trailing newline.
3. Проверка непустоты — 400 при пустом.
4. Проверка номера по алгоритму Луна — 422 при неуспехе.
5. Вызов `service.UploadOrder`: попытка INSERT в таблицу `orders`.
6. Если `ErrOrderAlreadyExists` — запрос `GetOrderByNumber` для определения владельца:
   - тот же пользователь → 200 (заказ уже загружен);
   - другой пользователь → 409.
7. Если `nil` — заказ новый, постановка в `accrualQueue`, ответ 202.

### `GET /api/user/orders` — список заказов

1. Извлечение ID пользователя из контекста.
2. `service.ListUserOrders`: SELECT с сортировкой `ORDER BY uploaded_at DESC`.
3. Если список пуст — 204.
4. Если не пуст — JSON-массив. Поле `accrual` включается только для заказов со статусом `PROCESSED` и положительным значением начисления (через `*jsonNumber` с `omitempty`). Значения `accrual` сериализуются как числа без кавычек (через кастомный `MarshalJSON`).
5. Ответ 200, `Content-Type: application/json`.

### `GET /api/user/balance` — текущий баланс

1. Извлечение ID пользователя из контекста.
2. `service.GetBalance`: один SELECT (`balance`, `withdrawn`).
3. Ответ 200, JSON `{current, withdrawn}`. Значения — `jsonNumber` (числа без кавычек). Баллы — `NUMERIC(12,2)` в БД, `decimal.Decimal` в Go.

### `POST /api/user/balance/withdraw` — списание баллов

1. Извлечение ID пользователя из контекста.
2. Чтение JSON-тела с полями `order` и `sum` (макс. 4096 байт).
3. Проверка непустоты номера — 400.
4. Проверка номера по Луну — 422.
5. Проверка `sum > 0` — 400 при нарушении.
6. `service.WithdrawPoints`: одна транзакция из четырёх шагов (см. «Транзакция списания»).
7. `ErrInsufficientFunds` → 402. `ErrOrderAlreadyExists` → 422 (см. замечание о 422 выше).
8. При успехе — 200.

### `GET /api/user/withdrawals` — список списаний

1. Извлечение ID пользователя из контекста.
2. `service.ListWithdrawals`: SELECT с сортировкой `ORDER BY processed_at DESC`.
3. Если список пуст — 204.
4. Если не пуст — JSON-массив, ответ 200.

### `GET /ping` — проверка БД

1. `service.Ping`: `pool.Ping`.
2. 200 при успехе, 500 при недоступности.
3. Без аутентификации.

## Канальная архитектура

### Обзор

Два буферизированных канала и пул воркеров образуют конвейер асинхронной обработки:

1. `accrualQueue` (буфер 2048) — канал номеров заказов для опроса accrual-системы.
2. **Worker Pool** — N воркеров (по умолчанию 5, настраивается через `ServiceConfig.AccrualWorkerCount`), каждый читает из `accrualQueue` и параллельно опрашивают accrual-систему.
3. `dbUpdateQueue` (буфер 512) — канал обновлений статусов и начислений для записи в БД.
4. **Batch Processor** — горутина, накапливающая обновления и пакетно записывающая их в БД.

```
StartAccrualProcessor
├── runAccrualWorkerPool (родительская горутина)
│   ├── pauseUntil atomic.Int64 (общая для всех воркеров)
│   ├── worker 0 → accrualWorkerLoop
│   ├── worker 1 → accrualWorkerLoop
│   ├── ...
│   └── wg.Wait() → close(dbUpdateQueue)
└── runBatchProcessor
```

### `accrualQueue` — очередь запросов к accrual-системе

Канал `chan string` размером 2048. Источники:

- `uploadOrder` — новый заказ после загрузки пользователем;
- `EnqueuePendingOrders` — startup-sweep при рестарте (см. ниже);
- `requeueOrder` — переотправка заказов в нефинальных статусах через задержку.

Функция `enqueueOrder` использует `select` с тремя ветками:

1. `<-s.closed` — сервис останавливается, отправка отменяется;
2. `s.accrualQueue <- orderNumber` — успешная отправка;
3. `default` — очередь переполнена, логируется предупреждение; заказ остаётся в БД со статусом `NEW` и будет обработан при рестарте.

### Worker Pool

N воркеров (`AccrualWorkerCount`, по умолчанию 5) читают заказы из `accrualQueue` и опрашивают accrual-систему. Каждый воркер вызывает `processOneOrder`, который маршрутизирует ответ:

1. **200, статус INVALID или PROCESSED** — отправка `OrderUpdate` в `dbUpdateQueue` (финальный статус).
2. **200, статус REGISTERED или PROCESSING** — отправка `OrderUpdate` в `dbUpdateQueue` (обновить на `PROCESSING`), заказ переотправляется в `accrualQueue` через `AccrualRetryDelay` (1 секунда).
3. **200, неизвестный статус** — логируется Warning, статус трактуется как `PROCESSING`, заказ переотправляется.
4. **204 (заказ не зарегистрирован)** — переотправка через `AccrualRetryDelay`.
5. **429 (превышен лимит)** — заказ переотправляется через задержку из `Retry-After`; все воркеры приостанавливаются (см. ниже).
6. **Ошибка сети / 5xx (после ретраев в клиенте)** — переотправка через `AccrualRetryDelay`.

Между запросами каждый воркер выдерживает `AccrualPollInterval` (100 мс, per-worker). Эффективный rate = `workerCount / AccrualPollInterval`.

**Обработка 429 — пауза всех воркеров.** Все воркеры разделяют `pauseUntil` (`atomic.Int64`) — Unix-наносекунды, до которых отправка приостановлена. Воркер, получивший 429, вычисляет `time.Now().Add(Retry-After)` и через CAS-цикл сохраняет максимальное значение в `pauseUntil`. Перед каждым запросом воркер проверяет `pauseUntil`: если текущее время раньше — ждёт до него через `select` с `time.After` / `closed` / `ctx.Done()`. После истечения паузы значение сбрасывается в 0. Это позволяет всем воркерам приостановиться одновременно, а не только тому, кто получил 429.

**`requeueOrder`.** Использует `time.AfterFunc(delay, func() { s.enqueueOrder(orderNumber) })`. При срабатывании `enqueueOrder` проверяет `closed` и безопасно отменяет отправку, если сервис останавливается.

### `dbUpdateQueue` — очередь обновлений БД

Канал `chan repository.OrderUpdate` размером 512. Источник — только accrual-воркеры. Родительская горутина `runAccrualWorkerPool` закрывает этот канал после `wg.Wait()` (дожидаясь всех воркеров), что каскадно останавливает batch processor.

Отправка — блокирующая. Если очередь переполнена (БД не справляется), accrual-воркеры приостанавливаются — естественный backpressure.

### Batch Processor

Накапливает обновления и сбрасывает в БД по двум триггерам:

1. Размер батча достиг `DBUpdateBatchSize` (128);
2. `time.Ticker` каждые `DBUpdateFlushTimeout` (200 мс).

Сброс — синхронный (без отдельной горутины), гарантирует порядок записи. Использует свежий контекст с таймаутом `flushTimeout` (10 секунд, константа) — финальный батч при остановке не потеряется даже если основной контекст отменён.

`BatchUpdateOrders` выполняет все обновления в одной транзакции: `UPDATE orders SET status = $1::order_status, accrual = $2 WHERE number = $3` (с явным cast для enum), а для `PROCESSED` с положительным accrual — дополнительный `UPDATE users SET balance = balance + accrual`. Запросы выполняются без прекомпиляции, поскольку для коротких батчей (до 128 элементов) overhead от Prepare может превысить выгоду.

### Graceful shutdown

1. Сигнал ОС → отмена `ctx` → `server.Shutdown` (до `ShutdownTimeout` = 10 секунд).
2. `StopAccrualProcessor` → `closeOnce.Do(close(closed))` — запрещает новые отправки в `accrualQueue`.
3. `enqueueOrder` и callback-функции `time.AfterFunc` видят `closed` — новые отправки отменяются.
4. Воркеры выходят по `closed` или `ctx.Done()`.
5. `runAccrualWorkerPool` дожидается всех воркеров (`wg.Wait()`) и закрывает `dbUpdateQueue`.
6. `runBatchProcessor` делает финальный `flush` и выходит.
7. `main.go` ждёт `backgroundWg`.

**Канал `accrualQueue` намеренно не закрывается** — это предотвращает panic в callback-функциях `time.AfterFunc` из `requeueOrder`, которые могут сработать после `StopAccrualProcessor`.

### Startup-sweep

При запуске `EnqueuePendingOrders` выбирает из БД заказы в статусах `NEW` и `PROCESSING` и ставит их в `accrualQueue`. Это гарантирует, что заказы, не дошедшие до accrual при предыдущей остановке, не потеряются.
